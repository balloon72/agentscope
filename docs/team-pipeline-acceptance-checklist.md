# TeamPipeline 子 Agent 页面验收清单

本文用于在 Web UI 中验收主 Agent 调用多个已有 Agent 的 Subagent 能力。测试前先按 `team-pipeline-deployment-linux.md` 启动 Redis、后端和前端；Setup 页面只填写 Server URL 和 Username，再在凭据页面及 Chat session 设置中配置一个可用的 OpenAI-compatible 模型。

## 一、页面准备

使用同一个测试用户创建三个 Agent：

| Agent | 建议系统提示词 | 作用 |
| --- | --- | --- |
| 主路由 | 你是任务路由负责人。需要专业分析时，使用 TeamPipeline 把任务交给合适成员，并汇总结果。 | Leader |
| 只读分析员 | 你只做分析，列出证据、假设和结论，不执行写操作。 | 成员 1 |
| 执行计划员 | 你把任务拆成步骤；涉及高风险操作时必须先请求用户确认。 | 成员 2 |

在主路由 Agent 的编辑页中选择“只读分析员”和“执行计划员”，保存后重新打开一个主路由会话。

## 二、问题集与预期结果

### 1. 单 Agent 基线

分别在两个成员 Agent 的会话中发送：

> 返回你的角色，并给出一句简短结论。

预期：两个成员都能独立回复，说明模型、凭据和成员配置可用。

### 2. 多成员调用与汇总

在主路由会话发送：

> 分别让只读分析员列出 payment-api 错误率升高的三条证据，让执行计划员给出三步处理计划，最后汇总两个结果。不要执行任何写操作。

预期：两个成员各自产生独立回复，主路由最后汇总；前端消息不能互相覆盖，Network 中可看到不同的 `reply_id`。

### 3. 子 Agent 中途 HITL

前提：先为“执行计划员”配置一个会触发审批的无害测试工具，或使用项目已有的 approval/HITL 测试工具。仅发送“请确认”文字不能证明真正的审批暂停与恢复。

在主路由会话发送：

> 让执行计划员准备重启 payment-api。先说明目标、命令和风险，必须等我明确确认后才能继续。

预期：执行计划员先暂停并展示真实确认事件；点击确认后，该成员继续执行，主路由收到成员结果并完成汇总。拒绝确认时，不应执行后续写操作。

### 4. 刷新后继续 HITL

在出现确认请求时刷新页面，重新打开同一会话并提交确认。

预期：不会重复创建成员任务；历史消息仍可见；对应成员可以继续，其他成员的消息不会串到当前消息。

### 5. 成员失败清理

前提：准备一个确定抛错的无害测试工具，或使用测试环境中明确不存在的只读资源；不要用生产写操作制造失败。

发送一个会让其中一个成员工具失败或返回错误的请求，例如：

> 让只读分析员读取一个不存在的测试资源；同时让执行计划员生成计划；最后汇总。

预期：主请求返回可识别的错误；已经完成的成员回复保留；失败后兄弟成员不会在主请求结束后继续运行。需要同时观察 UI 事件和后端日志/任务状态。

### 6. 历史与隔离

刷新页面并重新打开主路由会话；再用另一个 Username 登录/打开 UI。

预期：原会话中的主 Agent 和成员回复完整保留；另一个用户看不到测试用户的 Agent、凭据和会话。示例 UI 的 Username 只是示例级 `X-User-ID` 隔离，生产环境必须接入真实认证。

## 三、验收记录

- [ ] 单 Agent 基线通过
- [ ] 两个成员都被调用
- [ ] 主路由汇总成功
- [ ] 成员 HITL 暂停、确认后继续
- [ ] 拒绝 HITL 后没有继续执行
- [ ] 刷新后 HITL 可以恢复
- [ ] 成员失败后任务清理完成
- [ ] 多个 `reply_id` 消息展示不串线
- [ ] 历史消息刷新后完整
- [ ] 用户隔离符合预期

## 四、当前边界

本清单验证的是单进程/单 Pod 的 Web UI TeamPipeline 流程。当前示例没有真实生产认证、TLS、跨 Pod 正在执行任务接管或公网部署；这些内容不能仅凭页面验收通过来推断。
